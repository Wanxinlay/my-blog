**结论先说：这套系统的技术部分基本都做成了，产品部分只有一个失败——没有解决「数据怎么进来」。而一个工具无论做得多好，只要数据进不来，它就不存在。**

2026 年 9 月，我用 3 周时间自建了一套个人管理系统：资产记账、简历管理、笔记、门户四个本地服务，共 9,128 行代码。第 4 周，我把它停用、归档、删除了。这篇复盘公开全部过程、决定终止的使用数据，以及我认为最值得带走的方法。

## 一、项目概况

### 做成了什么

| 服务 | 功能 | 结局 |
|---|---|---|
| 资产 | 记账 / 资产负债 / 投资估值 / 财务比率 | 删除 |
| 简历 | 素材管理 + 一页 A4 PDF 导出 | 删除 |
| 笔记 | Markdown + 标签 + 跨域引用 | 删除 |
| 门户 | 只读聚合 | 删除 |

外挂设施：每日自动备份（保留 7 份）、每日数据维护、67 项回归自检。

## 二、搭建阶段的经验（技术）

### 2.1 三层验证手法 ★ 最值得带走

**单测通过 ≠ 页面正确。** 必须分三层验，缺一层就有一类 bug 抓不到。

| 层 | 手法 | 能抓什么 |
|---|---|---|
| L1 静态 | `bash -n` × 脚本、`plutil -lint` × plist、`py_compile` × py、`node --check` × js | 语法错、配置格式错 |
| L2 端口级 | 起**临时端口**真发 HTTP，**逐资源**探页面（不是只探 `/health`） | 路由错、鉴权错、静态资源 503 |
| L3 渲染级 | Node **假 DOM 真执行**前端脚本，对 `innerHTML` 做结构与数值断言 | **逻辑错**：`map` 传参顺序、前后缀拼接、`NaN` 渲染、`undefined` 泄漏 |

**为什么 L3 不可省**：`node --check` 完全抓不到这类错——

```js
points.map(dot)          // 实际传入 (元素, 下标)
function dot(p, i) {...} // 期望 (点, 索引)
```

语法合法、运行不报错，页面渲染出一堆 `NaN`。**只有真执行 + 断言能抓。**

**写假 DOM 桩时的两个必踩坑**：

1. 桩必须给 `<select>` 加 `options: []`。否则 `[...sel.options]` 抛错，而异常被 `load()` 的 `catch` 吞成一条 toast——症状是「前面元素渲染了、后面全空」，极像业务 bug。**排查口诀：先读 toast 的文本内容**，真实错误就在里面。
2. `let S` 是词法绑定，不挂 `globalThis`，且 `load()` 会重新赋值它。在脚本末尾存引用只会拿到初始空对象——必须在 `setTimeout` 里用 `vm.runInContext('S', sandbox)` **现取**。

**另两条实战教训**：

- `test_client()` 只覆盖 WSGI 层，**验不到真实 HTTP 与静态资源**，必须起临时端口。
- **逐资源探页面**，不能只探 `/health`。曾出现软链接少一层导致 `/health` 仍 200、而首页和静态资源全 503 的情况。

### 2.2 多服务本地架构：一域 = 一进程 + 一端口 + 一库

四个服务各自独立进程、独立端口、独立 SQLite 库。**硬规则：禁跨库外键、禁服务间 HTTP 调用。** 跨域引用只做「软引用 + 格式校验」（如 `fin:trans:42`），不校验存在性。

**收益**：任一服务可单独停、单独重写、单独搬走，不牵连其他；崩溃面被限制在一个域内。

**两个让目录可整体搬迁的做法**：

- **配置单点**：端口统一读一份配置文件，各服务都不写死。
- **路径反推**：用工具函数从脚本自身位置反推仓库根，不依赖绝对路径。

**验证手法**：逐站 import 后断言端口与配置一致，且各路径常量指向的位置真实存在。

### 2.3 SQLite 在线备份

**必须用 SQLite 的在线备份 API，不是文件拷贝**——WAL 模式下直接 `cp` 可能拿到不一致的快照。

每份备份包含：数据库 + 业务数据目录 + 配置 + 校验和清单 + 元数据。保留 7 份，每日定时触发，配套写恢复手册。

**实测**：连续 7 天正常产出，无一次失败。**成本极低，收益是「敢动手改」。**

### 2.4 一页 A4 PDF 导出（简历）

三条硬约束，缺一不可：

1. **尺寸写死毫米**，不用相对单位
2. **样式表全用 `em`**，让整体随基准字号等比缩放
3. **用 JS 计算缩放因子**（本例下限 0.65）

**禁用 `zoom` 与 `transform` 做缩放**——它们会触发 Chrome 打印时的「缩到合适」假成功：表面上排进一页了，实际输出被二次缩放，字体大小失控。

改版式后必须跑 PDF 校验回归。

### 2.5 零构建静态前端 + 共用设计令牌

- 抽一份共用表现层（tokens / base / shell / components），各站点引同一套 CSS
- **视觉约束**：颜色只有黑 / 白 / 灰 + 一个链接蓝；层次全靠 1px 细线；**全站无 `box-shadow`**；圆角 ≤12px；禁渐变、emoji 导航、彩色标签墙
- 图表**禁引图表库**，手写 SVG 或单色 CSS 条
- **SVG 坑**：只能写内联 `style="stroke:var(--chart-N)"`，写成 `stroke="var(--x)"` **属性不生效**

**收益**：改样式不需要构建、不需要重启（开发服务器每次请求现读磁盘），比对校验和即可确认线上已生效。

### 2.6 本地服务的安全底线

- 所有 API 需自定义请求头令牌（令牌文件权限 0600）
- 页面靠注入一段脚本**劫持 `fetch` 自动补头**，前端业务代码无需感知令牌
- CORS 只回白名单（本机地址 × 端口），**禁用 `Access-Control-Allow-Origin: *`**
- 健康检查端点免令牌，且只吐非敏感信息
- 所有 HTML 响应加 `Cache-Control: no-store`
- 沙箱内调试本机端口**必须绕过系统代理**（否则被代理软件劫持）

### 2.7 数据口径的工程化

经济学上的口径问题最后都变成了代码里的断言。留下来三条：

1. **符号约定要显式写进注释与文档**。本例：信用账户的余额表示**欠款（正数为欠）**；信用额度独立成列，**既不计资产也不计负债**。验收标准写成一句人话：*「信用卡不使用的时候，资产和负债都不该变。」*
2. **存量与流量不能混算**。曾把「累计支出 ÷ 资产总额」当财务指标——这是**存量除流量**，量纲不对且必然单调趋近 100%。正确做法是同量纲比较（本月支出 ÷ 本月收入）或年化（年化支出 ÷ 净资产）。
3. **分母为 0 返回空值，不返回 `Infinity`，也不伪装成 0**。前端统一显示「—」。

**比功能测试更能防回归的是「哨兵断言」**：

- *「信用额度翻倍，汇总结果不变」*——防止额度混进汇总
- *「新表为空时，结果与升级前逐分一致」*——防止新增逻辑污染旧口径

**实现要点**：新口径的换算只发生在一个边界层，核心汇总函数保持**纯函数**（只做加减法）。否则上面两条断言都会破。

### 2.8 批量改源码的安全做法

把改动写成 `(文件, 旧串, 新串)` 的列表，逐条检查「旧串在该文件中的出现次数 == 1」，不等于 1 就报错拒写。避免「改到了不该改的地方」这类难以察觉的错误。

### 2.9 macOS 环境适配经验

| 事项 | 结论 |
|---|---|
| launchd 读 plist 的时机 | **只在登录时** → plist 必须以仓库内副本为唯一真源，改完需重新装载或重新登录 |
| 重启进程 | `launchctl kickstart -k` 实测可用 → 改后端可自行重启 |
| `launchctl list` 返回空 | 改用 `launchctl print gui/$(id -u)/<label>` |
| 无头 Chrome | 受限环境下可能完全不可用 → 前端验证改走 Node 假 DOM |
| BSD `grep` | 对含中文的源文件会漏匹配；`\|` 交替不生效，须用 `grep -E` |
| 同一文件连发两个编辑 | 后者可能**静默覆盖**前者 → 一次只改一处，改完立刻复核 |

### 2.10 目录改名可以零停机

服务的路径依赖全部通过「反推仓库根」解决后，整个目录可以随意改名搬迁，不需要改任何代码——只要定时任务配置里的绝对路径同步更新。这让「重组目录结构」这种高风险操作变成了低风险操作。

## 三、使用阶段的经验（这一部分比技术更值钱）

### 3.1 输入成本是生死线，功能数量不是

**整个项目唯一真正的失败：没有解决「数据怎么进来」。**

交付顺序是：

```
口径修正 → UI 重构 → 目录重组 → 投资估值 → 财务健康比率 → …… → 账单导入（从未做）
```

所有分析功能的前提都是「数据进得来」，而这件事被排在了最后。结果：**交付的估值功能使用次数 = 0。**

**输入成本的具体账**：

| | 消费少的时期 | 消费多的时期 |
|---|---|---|
| 每日消费笔数 | 1–2 | 5–13 |
| 每笔录入成本 | ~20 秒 | ~20 秒 |
| **每日总成本** | **~40 秒** | **~3–5 分钟** |
| 感知收益（知道钱花哪了） | 恒定 | 恒定 |

成本随场景变化、收益不随场景变化——这是一个**结构性必赔的账**。无论用什么工具、靠什么纪律，只要输入仍由人逐笔完成，结果都相同。

这不是执行力问题。主流记账 App 评测的标题就是「手动记账是一件反人性的事」，行业共识与个人经历完全一致。

**崩盘的形态是可观测的**：日常纪律衰减 → 补记批次越来越大 → 最终放弃。本例中最后一笔记录发生在一次补录 26 条（占全部记录 28%）之后的第二天。

### 3.2 不要把「某个功能做错了」当成「整个方向错了」

记账失败后，很容易得出「自建不如买」的结论。但逐项归因后结果完全不同：

| 失败项 | 是「自建」的锅吗 | 判断依据 |
|---|---|---|
| 记账坚持不下来 | **否** | 任何手工录入工具都一样，换 App 不解决，换**输入方式**才解决 |
| 账单分类辨识不清 | **否** | 这是分类规则问题；开源工具已有「规则 + LLM 分类 + 记忆映射」的成熟解 |
| 笔记没人用 | **是** | Obsidian 免费、本地 Markdown、1700+ 插件，自建零胜算 |
| 简历使用率低 | **否** | 简历工具天然一年用两周。**低频 ≠ 无用** |
| 维护成本 | **部分是** | 4 个常驻服务 + 加固 + 回归 + 备份是一笔固定开销 |

**结论：唯一被真正证伪的是「自建笔记」。记账失败是设计（输入方式）问题，不是路线问题。**

**教训：判死一个系统前，先逐项归因。** 否则会把「某个功能做错了」当成「整个方向错了」，也可能反过来把「方向错了」误判成「再努把力就行」。

### 3.3 不要为「可能有价值」的分析功能先建库

估值表的结构设计得很周到（同日幂等、支持 CSV 导入、空表时优雅回退旧口径），配套写了端点、前端、完整性检查、回归断言——**然后一行数据都没进来。**

**教训：数据表的第一个真实 `INSERT`，应该比表结构的设计更早出现。** 先手工确认「我真的会往里填数」，再建表和端点。

### 3.4 「使用率低」和「没人需要」要分清

简历服务在使用窗口内 20 天没被打开过。按「使用频率」排序，它排在最后一名；但它的 8 条素材是整份归档里**唯一有实质内容的个人资产**。

**低频高价值的工具真实存在。** 用「打开次数」去评判一个「一年用两周」的工具，会得出错误结论。

### 3.5 复盘必须用客观行为数据，不能靠感觉

「感觉没什么用」和「92 条记录、10 月零新增、估值表 0 行」是两回事。后者才能支撑决策。

**可用的五项客观证据**：

1. **各表的行数**——规模
2. **最后一次写入的时间**（以及距今多久）——活性
3. **访问日志里的写操作时间线**——区分「打开过」和「用过」
4. **记录的创建时间批次分布**——能看出「补记雪崩」发生的时点
5. **交付的功能 vs 对应数据的行数**——能看出「做了但没人用」

### 3.6 没有版本控制的代价

整个项目**没有 git 仓库**。3 周内的所有改动无法回溯，做复盘时只能靠文件修改时间反推。

**教训：本机个人项目同样需要 git。** 成本几乎为零（`git init` + 一次提交），收益是「敢改」。

### 3.7 自建 vs 成熟产品：判断标准要在动手前用

自建只在一种情况下成立：**成熟产品做不了，或者做得很难受。**

- 笔记 → 成熟产品完胜（免费、本地 Markdown、1700+ 插件）→ **不该自建**
- 跨市场多币种资产估值（多币种 + 多市场基金/ETF）→ 主流记账 App 不擅长 → **值得自建**

**这个判断要在动手前做，不是做完之后。**

### 3.8 如果重来一次，正确的顺序是什么

1. **先解决输入**——用现成的自动记账工具（监听通知栏抓取支付通知，或账单文件 + 现成解析器），不自研解析器
2. **等第一笔真实数据自然流入**——确认输入链路真的活着
3. **再考虑建库**——只建「已经被填过数」的表
4. **再做分析**——报表、比率、趋势
5. **最后做界面美化**——UI 只影响体验，不影响存亡

这个顺序的反面就是实际发生的顺序：先做了最漂亮的界面和最精致的分析，唯独把「数据从哪来」留到了最后。

## 四、可复用资产清单

以下六项在别的项目里可以直接复用，与「个人管理系统」这个具体形态无关：

| # | 资产 | 适用场景 |
|---|---|---|
| 1 | **三层验证手法**（静态 / 端口级 / 渲染级）+ 假 DOM 桩的两个坑 | 任何 Web 应用 |
| 2 | **SQLite 在线备份 + 校验和 + 恢复手册** | 任何本机 SQLite 应用 |
| 3 | **恰好一页 A4 的 PDF 导出三条硬约束** | 简历、报告、单据 |
| 4 | **零构建静态前端 + 共用设计令牌 + 灰阶手写 SVG** | 任何「不想要构建链」的小型工具 |
| 5 | **多服务本地隔离架构**（一域一进程一端口一库 + 配置单点 + 路径反推） | 多模块本地工具 |
| 6 | **本地服务安全底线**（令牌头 + fetch 劫持注入 + CORS 白名单 + no-store） | 任何监听本机端口的服务 |

## 五、下次做个人工具前的检查表

1. **输入成本是多少？** 具体到「每笔 X 秒 × 每天 Y 次 = 每天 Z 分钟」。超过 1 分钟就要先解决它。
2. **这个输入动作能坚持多久？** 把「最好的时期」和「最忙的时期」分别算一遍。
3. **成熟产品做得了吗？** 做得了就别自建。
4. **有没有现成的引擎可以复用？**（解析器、格式转换、导出库……）
5. **第一个真实数据什么时候进来？** 如果超过一天，说明设计有问题。
6. **`git init` 了吗？**
7. **怎么验证？** 静态 / 端口级 / 渲染级，三层各写一条。
8. **维护成本是多少？** 几个常驻进程、几个定时任务、多少固定开销。
9. **「使用率低」和「没用」分清了吗？** 有些工具本来就是低频高价值的。
10. **如果这个项目失败，我能带走什么？** 先想清楚，再动手。

## 结语

这套系统在工程上是成立的：服务稳定运行、备份连续产出、回归自检可信、界面统一、数据全在本机。

它失败的地方非常具体——**把「每天手动录入」当成了理所当然的前提**。这是一个设计决策，不是能力问题。

如果还有下一次：**先让数据自己流进来，再谈分析。**

这个教训后来直接改变了我用 AI 的方式：不再让 AI 帮我「做一个更好的录入界面」，而是让它接管输入本身——语音口述、自动转写、自动整理入库。输入成本降到接近零之后，系统才真正活了下来。
